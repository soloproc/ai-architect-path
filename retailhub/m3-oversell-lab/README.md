# M3：隔离级别与超卖实验（对应《卷03 数据密集型系统》本卷实战 · 任务二）

> 教程原文：*读十遍"丢失更新"的定义，不如亲手让它发生一次再消灭它。*
> 本实验与教程中 `isolation-oversell` 交互 Demo 的叙事完全对应：
> 多个买家并发抢 stock=5 的商品——先看"Read Committed · 先读后写"
> 怎么把库存扣成负数，再看"原子 UPDATE"怎么让多余的买家安全失败。

## 实验设定

- 商品 `SKU-1001`，初始库存 **stock = 5**（`lab/seed.py` 确定性种子，每次实验重建数据库）。
- **6 个并发买家**，每人买 1 件，总需求 6 > 库存 5。
- 用 `threading.Barrier` 强制所有买家"先一起读完库存，再一起扣减"，
  把生产环境毫秒级的竞态窗口放大成确定性事件。

## 运行步骤

```bash
cd retailhub/m3-oversell-lab
python3 lab/seed.py      # 可选：先看种子数据
python3 lab/naive.py     # 错误示范：读库存→判断→扣减
python3 lab/atomic.py    # 正确方案：原子 UPDATE + 持锁事务
```

（只依赖 Python ≥ 3.11 标准库，无需安装任何东西。）

## 预期输出对照

### `naive.py` —— 必现超卖

时间线里可以看到 6 个线程全部读到 `stock = 5`、全部判断通过：

```
  时刻(ms)  线程    事件
     0.3    T1      SELECT 读到 stock = 5
     0.4    T2      SELECT 读到 stock = 5
     ...    (6 个线程都读到同一个旧值 5)
    22.1    T1      判断通过（stock=5 >= 1），准备扣减
    ...
    25.0    T6      UPDATE stock = 5 - 1，下单成功 ✓
------------------------------------------------------------
初始库存 = 5，买家 = 6，成交单数 = 6，最终库存 = -1
❌ 超卖发生：库存被扣成负数，卖出的件数超过了实际库存。
```

多跑几次（`for i in {1..5}; do python3 lab/naive.py; done`），
最终库存恒为 **-1**、成交恒为 **6 单**——超卖是结构性的，不是运气。

### `atomic.py` —— 永不超卖

方案 A（原子 UPDATE）与方案 B（BEGIN IMMEDIATE 持锁事务）的输出都是：

```
初始库存 = 5，买家 = 6，成交单数 = 5，最终库存 = 0
✅ 正确：5 人成交、1 人安全失败，库存恰好为 0，永不超卖。
```

区别只在失败方式：方案 A 的第 6 个买家 `影响行数 = 0`；
方案 B 的第 6 个买家在事务内读到 `stock=0` 主动回滚。

## 关键结论（与教程口径一致）

防住超卖的是**原子操作带来的单行互斥，与数据库默认隔离级别无关**。
naive.py 的错不在 Read Committed，而在"判断依据（旧值）和写入
不是同一条原子语句"。工程排序：**能用原子操作就不用锁，
能用锁就不上串行化**——所以方案 A 是生产首选。

## 思考题（对应卷03 实战验收）

1. 把 naive.py 的数据库换成默认 Read Committed 的 PostgreSQL，
   超卖会消失吗？为什么？（提示：先想清楚 Read Committed 保证的
   到底是什么——"读不到未提交的数据"，而不是"读到的值在我写之前不变"。）
2. 方案 A 的 `WHERE stock >= ?` 条件如果被删掉（无条件 `stock = stock - 1`），
   最终库存会变成多少？这条 UPDATE 还是原子的，为什么仍然出错？
3. 教程提到的**写倾斜**（两个客服同时关闭"最后一个营业中的门店"）
   能用方案 A 的原子 UPDATE 防住吗？如果不能，为什么？该用什么？
4. 方案 B 在 SQLite 用 `BEGIN IMMEDIATE`，在 PostgreSQL 里对应什么写法？
   它相比方案 A 多付出了什么代价？（从锁持有时间和吞吐角度回答。）
